## 程序、数据与资源

```text
Program Root                       Data Root
├─ SeedLab Control Center.exe       ├─ data/seedlab.db
├─ SeedLabServer.exe                ├─ config/seedlab.json
├─ _internal/                      ├─ config/instance.json
├─ app/web/                        ├─ logs/
├─ app/migrations/                 └─ backups/
└─ config/installation.json            ├─ auto/

```

RuntimePaths显式解析program_root、resource_root、data_root及development/portable布局，不依赖cwd。源码资源是frontend/dist与backend/alembic；portable资源是app/web与app/migrations。安装定位文件保存Data Root绝对路径；移动程序不改变数据位置。正式数据、日志与备份只进入独立Data Root，程序资源只读。

只有不可替代的正式seedlab.db进入备份机制。源码由Git保存，运行配置、日志、测试库、EXE/ZIP、构建中间物、依赖、截图和导出不另建历史备份体系。build/dist仍为被忽略的可再生成产物目录；AF-1 保持已验收分发产物原样。AF-1 已授权的 before-upgrade 和 failed-recovery 仅保护数据库恢复点与故障数据库，不扩大为配置、源码或日志归档。超出这些类别仍须先STOP并由用户确认。

## 首次部署、复用与实例归属

五步向导选择长期数据目录、访问方式、端口和备份设置。正式首次部署拒绝TEMP路径，提前检查端口；冲突时返回访问步骤，不接管占用者、不自动换端口。程序config首次需要可写，写入失败提示移动程序，不提权或使用VirtualStore。

新空目录初始化迁移、独立身份和一次性初始化码；首位管理员由网页/setup创建。已有目录须有合法配置、可识别迁移、完整性及外键检查通过，用户明确选择复用后沿用账号；未知、损坏或不完整目录拒绝且保留。完成向导后启动服务，账号和初始化状态仍由既有后端管理。

Data Root/config/instance.json保存部署编号及本机探测凭据。公开/api/health只返回状态与VERSION；携带本部署凭据的控制中心才能查询身份与运行参数。控制中心核对身份、数据路径、端口、访问方式、监听地址和自己启动的进程；另一份部署或缺少身份的旧服务均不接管，也不读取账号状态或提供启停。

QLocalServer/QLocalSocket按当前Windows用户会话分别对程序目录与数据目录建立单实例。相同程序或数据重复启动只激活已有窗口并退出0，不同部署不会被全会话锁混为一体。异常退出后端点可恢复。

## 单端口服务与前端路由

生产浏览器页面和/api由同一个FastAPI/Uvicorn端口提供；前端API使用同源相对路径。开发保持Vite 5173与FastAPI 8000，由Vite代理/api。

`app.server_entry`为共享服务器入口，源码runner与冻结EXE调用同一入口。原正式 v0.5.1 在检查前端和路径后直接通过共享迁移API升级，再启动单worker服务。AF-1 源码改为先经过下述统一数据库升级准备协议，成功后才构造 FastAPI 并启动 Uvicorn；首次部署及复用目录也接入同一协议。源码生产启动不运行npm/Vite；production关闭/docs及OpenAPI，development保持开发文档。

`SEEDLAB_WEB_ROOT`的源码相对路径锚定仓库，--web-root优先于配置。静态文件限制目录边界，未知/api、缺失assets、明显文件请求、路径穿越及外部链接返回404。普通无扩展名的页面请求回退index.html，页面路由由Vue Router唯一维护。

未显式指定数据库的源码runner使用开发.env与原开发路径；显式正式目标不读取仓库.env。自动验证使用独立临时数据库，不迁移或重置生产库。

| 访问方式 | 监听 | 用户入口 | Cookie Secure |
|---|---|---|---|
| 仅本机 | 127.0.0.1 | 本机HTTP地址 | false |
| 局域网共享 | 0.0.0.0 | 所选局域网IPv4地址 | false |

端口默认8848；内部健康检查始终使用本机地址。会话、账号和权限沿用后端认证规则。网络保存后重启服务，再以实际响应确认生效；已保存草稿不代替实际运行状态。

Qt枚举有效IPv4，不自动写回失效地址；网络及防火墙由用户管理。远程地址只接受无账号、路径、查询或片段的HTTPS根地址。远程检测检查证书、status与VERSION，独立于本机服务状态；不跟随重定向或忽略SSL错误。SakuraFrp由独立客户端管理，控制中心不保存其账号或凭据，也不启动/停止它。

## 控制中心与配置

control_center 分离路径、进程、配置、网络、窗口、主题和复用控件。v0.6.0 导航为概览、运行管理、网络访问、数据与备份、系统升级、日志与诊断、设置与关于；管理员恢复位于设置与关于，不增加业务模型。

配置位于Data Root/config/seedlab.json，安装定位位于Program Root。未知schema、非法字段/JSON或地址保留原文件并提示；只有明确保存才写入。保存使用同目录唯一临时文件、flush/fsync与os.replace，失败保持原配置。schema1的auto_start_server缺省false，旧配置缺字段兼容；自动备份默认开启并保留14份。

服务器由RuntimePaths生成命令，Windows隐藏启动。异步健康检查与服务管理不阻塞窗口；服务启动、停止、重启期间禁用冲突操作。正常停止使用独立stop-file，完成请求与lifespan后退出；超时提供继续等待或用户明确强制结束，只操作自己拥有的进程。

X隐藏至托盘，托盘不可用时最小化；退出运行中的服务须正常停止后再关闭。初始化码默认遮蔽，按需显示/复制，初始化完成后提示消失；不写日志。日志UTF-8、脱敏轮换，每份最多5MB，当前加两份轮换，不长期归档。

可选Windows登录启动只管理HKCU Run中的SeedLabControlCenter值，默认关闭、开发模式禁用；带引号EXE路径加--startup。移动程序后由用户明确保存更新。--startup在已部署时留托盘，未部署时显示向导。品牌ICO、PNG、EXE版本资源、任务栏与通知统一维护。

## 正式数据库备份与检查

sqlite_backup服务通过SQLite backup API从只读源建立一致性快照，支持WAL，不裸复制主库。后台写唯一partial，检查integrity/FK，fsync后发布，不覆盖已有文件；失败只清理本次partial和sidecar。超时会终止本次备份。

自动备份在本控制中心拥有的服务当天首次成功运行后按实验室日期检查，不是固定凌晨任务；已有当天有效备份则不重复。这一时点在 migration 之后，不能代替升级前恢复点。默认保留14份，可配置1—90。淘汰只接受auto内严格命名、有效日期、普通文件、无重定向/sidecar且完整性与外键通过的快照。manual、before-upgrade、failed-recovery、未知文件和历史快照不参与自动淘汰。

手工备份可在服务运行或停止时执行，永不被自动删除。后台串行检查不修改业务数据；失败提示停止录入并保留文件，不自动修复。退出等待后台任务完成。

## Managed Deployment：v0.6.0

~~~text
SeedLabRoot/
  SeedLab Launcher.exe
  SeedLab Updater.exe
  App/v0.5.1/SeedLab/                 完整旧 portable
  App/v0.6.0/SeedLab/                 完整新 portable
  Updates/                           本地包准备与失败现场
  Logs/                              升级诊断，轮换、不长期归档
  state/deployment.json
Data Root/                           可在 Root/Data，也可在外部；原地保留
  data/seedlab.db
  config/
  backups/                           唯一业务备份位置
  logs/
~~~

Launcher 仅使用标准库读取部署状态、选择 current Control Center，发现 pending 时打开独立 Updater，不猜测其他目录。缺少数据库或配置时拒绝启动，不走空库初始化。Launcher 和 Updater 分别 onefile 打包，Updater 自带 Qt/Python 及必要数据库库，不从 current App 的 `_internal` 加载。运行中的 EXE 和 DLL 在 Windows 上被占用，因此只安装新 slot，绝不覆盖当前 portable，也不使用 junction/symlink。普通可写目录和当前 Windows 用户足够，不申请管理员权限；不可写或不能确认进程归属时停止并提示。

部署状态为 format_version、current、previous、data_root、pending、rollback_snapshot。slot 保存版本、绝对程序位置、build_identity 和 revision；pending 只保存任务编号、阶段、目标、快照引用与可读原因。状态同目录 flush/fsync/原子替换，升级操作持有非阻塞文件锁。Data Root 不允许落入 App、Updates、Logs 或 state 管理区，不移动、不新建替代库。每次成功后只记录一个 previous；仅清理更早、带 managed 标记、无运行数据且无进程占用的自有标准 slot，外部 legacy 目录与失败现场保留。

### v0.5.1 首次升级

双击 `SeedLab-v0.6.0-Upgrade.exe`。助手从运行中的原控制中心、自身附近目录和当前用户已有登录启动记录寻找旧程序；不能唯一定位时，用文件选择器选择原 `SeedLab Control Center.exe`。读取其 PE 版本及 `config/installation.json`，核对原 Data Root、配置、完整性、外键与 revision，不要求用户寻找数据库。

已有 `Root/App/v0.5.1/SeedLab` 直接复用。非标准布局建议在旧目录旁创建 `SeedLabManaged`，状态引用原旧 portable，不复制旧 App、不搬数据。助手安装独立工具并原子记录旧 current；工具安装被中断时可再次使用同一助手补齐。用户确认程序保存位置、旧程序和数据位置；程序可继续运行时先准备包。

准备完成后，用户明确确认升级，并在旧控制中心选择“停止 SeedLab 并退出”。X 只隐藏至托盘。助手核对两个原 EXE 的完整路径、进程已退出和 Windows 文件占用；未完成退出则阻断，不批量 kill。首次成功后桌面 SeedLab 快捷方式指向 Launcher；原 HKCU Run 若启用且精确指向被接入的旧程序，则接续至 Launcher，原关闭状态或另一部署记录不接管。无关桌面快捷方式保留。接续失败不撤销已成功的升级，提示直接打开 Root 的 Launcher。

### 正常升级与 candidate

控制中心“系统升级”选择本地 ZIP，显示当前/目标版本、数据库是否需要调整及原数据位置。独立 Updater 继续检查并 staging；准备失败不停止当前服务，不改 current。用户在助手确认后，控制中心等待当前检查/备份、正常停止自己拥有的服务并真正退出，然后交给 Updater。

~~~text
本地 ZIP / CRC / 兼容性 → staging（旧程序仍运行）
→ 用户确认与正常退出 → AF-1 preflight（integrity / FK / revision）
→ 一份 before-upgrade snapshot + snapshot validation
→ AF-1 preparation → 安装新 slot / locator → candidate Control Center + Server
→ 身份与 health → 正常停止 candidate → offline postflight → 原子 commit
→ previous = 原 current → Launcher 打开新 current
~~~

本次 v0.5.1 → v0.6.0 的 head 均为 `d2e7a46b910c`，无需迁移，但软件升级仍创建恰好一份升级前快照；candidate 自动备份关闭，避免重复升级保护。适配层 `production_ops/database.py` 调用现有 inspect_schema、validate_database、database_lease、require_no_writer、BackupService、validate_snapshot、prepare_database_for_startup 和 postflight，不另写迁移引擎。目标 revision 来自包及随包迁移图；不同 revision 的包在停服前明确阻断，本版不自动跨 schema 升级。

candidate 核对版本、部署身份、数据位置、端口、访问方式、监听地址、候选编号及 Server PID 的 EXE 完整路径，确认 Control Center 仍存活。验证期间只允许 `/api/health`，其余请求返回可读维护提示，避免未提交版本接收业务写入。只有健康、进程正常退出和数据库 postflight 都成功后，才提交 current。提交前失败保留旧 current、pending、已发布快照和日志；下次 Launcher 进入恢复助手。普通界面不显示 traceback。

### 包契约与回退

`SeedLab-v0.6.0-upgrade.zip` 含 manifest.json 与 payload/SeedLab。manifest 字段为 format_version、target_application_version、supported_source_versions、target_alembic_revision、build_identity、updater_protocol、migration。采用完整 ZIP CRC、基本元数据一致性、必需资源/EXE 版本/迁移图检查和安全解包；拒绝 traversal、绝对/盘符路径、重复目标、重定向和混入运行数据。无逐文件 SHA manifest 或签名；构建报告可记录整个 ZIP 单一 SHA256。build-info 与 manifest 共用构建身份。

same-schema 恢复需用户确认并正常退出控制中心/服务，再验证上一程序兼容数据库。pending 恢复回原 current，已提交升级回 previous；只改变程序入口，不恢复数据库快照，保留升级后已有实验记录。旧 v0.5.1 回退入口打开其控制中心，是否自动启动服务沿用原配置，未开启时点击“启动 SeedLab”。数据库不能匹配上一程序时不给出有效恢复入口。

未来 schema-changing Rollback Set 仍为 Previous App + 对应 validated before-upgrade snapshot；state 可保存引用，显式数据库 restore 继续遵守下述 AF-1 contract。本版 GUI 不实现跨 schema restore，绝不 silent restore。当前仅 Local Package；executor 接受明确本地路径，与文件选择器和包来源解耦。未来远程检查/下载只提供本地 ZIP 后复用同一核心；当前没有联网、daemon、Windows Service 或 Updater 自更新。

## AF-1 源码：统一升级准备协议

共享入口为 services/database_upgrade.prepare_database_for_startup，server_entry 与部署初始化都调用它。底层 services/migrations 保留现有 Alembic chain，作为协调器的迁移执行器和临时测试工具；生产不得直接调用它绕开恢复点。

~~~text
显式数据文件与数据库使用锁
    ↓
迁移图完整且只有一个 head → 识别数据库 revision
    ↓
preflight：integrity_check + foreign_key_check
    ↓
当前 head：只读验证，直接允许启动；不迁移、不建立升级快照
已知祖先：SQLite backup → 验证快照 → Alembic forward migration → postflight
新版、未知、缺失或多个 revision：拒绝，保留原数据库
    ↓
只有 postflight 通过才允许 FastAPI/Uvicorn 启动
~~~

Application Version 与 Alembic revision 独立。目标与受支持祖先取自随程序交付的 ScriptDirectory 迁移图，不维护容易失真的手工 revision 列表。数据库 revision 不在该程序图中，包括新版数据库供旧程序打开时，均明确拒绝；不能据版本字符串猜测后继续运行。图多 head、缺失父节点、损坏数据库或 FK 问题也在迁移前拒绝。

第一次创建尚无业务表的新空库仍使用既有 Alembic 初始化，不为不存在的事实建立恢复快照。已配置部署的数据库文件丢失时拒绝启动，不静默创建空库替代。部署复用的配置、账号、身份及最终安装定位保存规则不变。

旧库升级按顺序验证原库、生成唯一 before-upgrade 快照、验证其 integrity/FK 和 source revision，再执行既有 forward migration。快照文件名含 source/target revision、实验室日期时间、Application Version 与随机后缀；同名不覆盖。轻量 `.upgrade.json` 原子写入状态及源/目标，失败时补充阶段与原因，不新增 metadata DB 或业务表。

postflight 再检查 integrity、FK、revision 等于唯一 target head，并只读查询少量核心表。兼容性、preflight、备份、快照验证、migration 或 postflight 任一失败均返回退出码1，服务器不启动；Control Center 及首次部署向导显示可理解的原因和下一步。数据库、已发布的恢复快照与失败日志保留，不自动恢复后假装成功，不静默删除故障现场。

数据库旁 `seedlab.db.operation.lock` 为小型持久锁文件，服务器从准备开始持有操作系统文件锁直至完全停止；文件保留但锁随进程退出释放。部署准备和恢复使用同一把锁，防止另一 SeedLab 进程并发升级或在线替换数据库。该文件不属于备份对象。

## AF-1 源码：显式数据库恢复

Rollback Set = Previous compatible application + Before-upgrade database snapshot。AF-1 先落实数据库侧操作；管理员须同时选择与快照匹配的完整程序。恢复旧快照后若仍启动较新程序，会按其迁移图再次受控升级；要回退运行就应使用兼容的旧程序。

操作前必须正常停止 SeedLab，并关闭所有 SQLite 数据库工具，包括空闲连接。恢复要求显式数据目录、备份和兼容程序的迁移资源路径，且必须带 `--confirm-stopped`；该参数是管理员确认，不替代实际占用检查。Windows 通过不共享的只读文件句柄检测其他程序占用，避免在检查失败库时触发 SQLite 清理 WAL；活动写入或文件占用均拒绝恢复。SeedLab 使用锁在整个恢复过程中持续持有。

恢复步骤：先核验选定快照为独立普通文件、integrity/FK 合格且 revision 受兼容程序支持；用 SQLite backup API 建立同目录唯一候选文件并再次验证/fsync。原数据库停用后，将原主库及存在的 WAL/SHM/journal 一起移动到唯一 failed-recovery 保留目录，随后以不覆盖目标的方式发布候选库。这里移动的是已停用故障文件，用于保留现场，不以裸复制活动数据库替代快照。发布后再次核验 integrity/FK/revision，记录选定快照与恢复时间，不自动启动服务，不调用 Legacy Importer。

发布前发生移动或写入失败时，仅在原位置仍为空的条件下放回已移动原文件，不覆盖后来出现的文件。发布后的验证或记录失败保留现状和证据，明确报告未完成，由管理员处理；没有静默回滚或自动启动。

下面是 **当前 AF-1 源码的管理员入口**。先把变量设为经过核验的完整路径，再从仓库根目录执行；日常实验人员无需运行该命令。操作不读取默认开发库。

~~~powershell
$dataRoot = '所选现有数据目录的完整路径'
$chosenSnapshot = '所选数据库恢复备份的完整路径'
$migrationRoot = (Resolve-Path -LiteralPath '.\backend\alembic').Path
Push-Location backend
try {
    ..\.venv\Scripts\python.exe -m app.recovery --data-root $dataRoot --snapshot $chosenSnapshot --migration-root $migrationRoot --confirm-stopped
} finally {
    Pop-Location
}
~~~

后续从 AF-1 源码构建的服务器亦有显式恢复模式，不需要启动前端或 Web 服务。**现有正式 v0.5.1 EXE 尚不包含这些参数**；AF-1 不重建或替换它。

~~~powershell
$programRoot = '包含 AF-1 恢复能力的完整程序目录'
& (Join-Path $programRoot 'SeedLabServer.exe') --database (Join-Path $dataRoot 'data\seedlab.db') --data-root $dataRoot --migration-root (Join-Path $programRoot 'app\migrations') --recover-from $chosenSnapshot --confirm-stopped
~~~

## 保留策略基础与 AF-1.x 边界

| 类别 | 产生时机 | 自动淘汰策略 |
| --- | --- | --- |
| auto | 本控制中心拥有的服务当天首次运行后，或既有自动备份检查 | 仅合格普通快照参与现有份数策略，默认14份 |
| manual | 用户明确执行手工备份 | 不自动删除 |
| before-upgrade | 已有受支持数据库确实需要 forward migration | 不自动删除，至少保护当前回退所需快照与状态 |
| failed-recovery | 显式恢复前保留故障主库及其事务附属文件 | 不自动删除故障现场 |

当前 before-upgrade / failed-recovery 采取完整保留，尚无自动归档清理、GFS 界面或回退集合自动选取；这保证不会被现有 auto 淘汰误删。配置与日志维持原运行用途，不建立额外历史备份。

Foundation 阶段未实现的 Current/Previous/Staging 现由 v0.6.0 离线部署核心落实，具体语义以上述 Managed Deployment 为准。多代历史、跨 schema Rollback Set GUI、在线检查/下载仍延期。AF-1 保持 migration 前有效恢复点与 startup fail-closed 的数据库唯一 authority。

AF-1 的[升级与恢复安全矩阵](../backend/tests/test_database_upgrade_recovery.py)及既有迁移数据保留测试只使用系统临时库，覆盖失败注入、跨进程占用、原文件保留和恢复后检查。固定历史回归源仍只读使用，不重复正式导入。代表性临时 SQLite 的 schema、integrity、FK、GER/measurement 与导出通过不能表述为正式生产库验证通过。

### 若未来另行验证真实生产副本
