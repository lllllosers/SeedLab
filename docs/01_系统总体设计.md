# 系统总体设计

SeedLab 是课题组内部的长期实验数据工作空间。当前稳定生产版本为 v0.5.1，已支持材料台账、GER 种子萌发试验、幼苗根苗长测定、科研工作簿、账号审计及 Windows portable。本文是架构唯一权威概览；具体业务规则、schema 和运维操作分别从[文档导航](README.md)进入。

## Current Architecture：当前实现

~~~text
Vue 3 / TypeScript / Pinia / Vue Router
    │ 同源 /api；开发由 Vite 代理
FastAPI routers（api）
    │ 权限与 HTTP 错误映射；部分查询与置床清单 XLSX 仍在 API
    ├──→ contracts（Experiment / GER / Measurement Pydantic 契约）
业务服务（services） ──→ contracts；↔ SQLAlchemy entities（models）
    │                      │
    └──────────────── SQLite WAL
                           ↑
                     Alembic migrations

AF-1 源码 runner / 后续冻结服务器 → app.server_entry
    → database_upgrade（兼容性、检查、按需快照）→ 既有 Alembic → 验证 → FastAPI/Uvicorn
Windows Control Center → 显式 RuntimePaths / 实例探测 / 进程 / SQLite backup
~~~

后端当前按 api、core、db、models、services 分目录，尚未按实验类型拆成独立模块。所有业务 ORM 实体仍集中在 models/entities.py；core/experiment_types.py 定义当前类型元数据、workflow Protocol 与不可动态注册的 registry；experiment_composition.py 静态组装唯一 GER 注册。Literal 输入范围继续保持 GER，以保留现有校验和 OpenAPI。应用 lifespan 绑定自己的 Session，导入模块不创建默认数据库；应用不自动建表，迁移只经 Alembic。

| 当前范围 | 真实入口与调用关系 |
| --- | --- |
| 平台与资源库 | core/auth、bootstrap、config 与 api/catalog、material_import；物种及种子批次是长期材料身份 |
| 实验配置 | api/experiments → Core identity/lifecycle；api/configuration → germination_config，GER 拥有方案、材料覆盖和 DAG |
| GER 执行 | api/execution → sowing_workflow、germination_execution；编号确认生成未置床计划皿，真实置床启动实验，巡检同事务生成前 N 株 |
| 幼苗测定 | api/measurement → seedling_measurement、measurement_query；从实际样本 × DAG 派生任务，SQL 分页/聚合，Python 校验写入 |
| 科研导出 | api/workbook_export → workbook_export → measurement_slots；从材料设计全集匹配真实事实，长表与宽表共用只读投影 |
| 生命周期 | experiment_lifecycle 为正式 status、started_at、ended_at、termination_reason 的唯一生产写入 authority；通过 registry 获取 GER 决策 |
| 审计 | services/application_support.record 随业务事务保存 AuditLog，common.record 保留兼容引用；audit_history 提供分页及业务身份，读取不新增审计 |
| 运维 | app/server_entry 和部署初始化共用 services/database_upgrade；现有 migration chain 不变，sqlite_backup 提供按需恢复点，database_recovery 提供停服后的显式恢复 |
| 前端 | generic experiment views 实际按 GER 配置；GerminationExecution 内含置床、巡检、测定工作台和记录，types.ts 集中维护类型 |

Python 材料排序及现场编号以 services/ordering.py 为单一权威来源。测定 SQL 使用该模块的编号表达式；SQL 查询按实验内编号、重复、皿内样本和 DAG 排序。中文名完整拼音的目录/材料排序当前在 Python 完成，没有第二套 SQL 拼音排序。

## AF-2：契约与依赖规则

`app/contracts/experiments.py`、`germination.py`、`measurement.py` 是当前 20 个增长域 DTO 的唯一定义；`base.py` 保存共享 ORMModel。API 与服务直接引用同一类型；`api/schemas.py` 仅兼容重导出这些类型，保留 Auth/Catalog 的原定义。字段、required/optional、默认值、校验与序列化不变；ProtocolInput 仍表达当前 GER 方案，不代表已拆分 Experiment Core。

增长域服务禁止依赖 `app.api.*`、FastAPI/Starlette、`app.main`、认证/Web adapter 或含 HTTP 兼容包装的 `services/common.py`。当前显式名单为 germination_config、germination_workflow、experiment_identity、experiment_lifecycle、germination_execution、sowing_workflow、seedling_measurement、measurement_query、measurement_slots、workbook_export、application_support。Contracts 同样不能依赖 API、services、models 或 db。新增增长服务时必须同步扩充架构测试名单，不能以换目录规避边界。

`contracts/errors.py` 只有 ApplicationError 及 NotFoundError、ConflictError、ValidationError；它们保存原业务 detail，不含 HTTP 状态。`api/errors.py` 分别映射为原 404、409、422，并复用 FastAPI 响应处理器。未分类异常保持服务器失败；请求体校验、Auth/CSRF 和 API 自身的 HTTPException 保持原路径。

`application_support.py` 提供事务、实体查找与审计实现，不依赖 transport；`common.py` 为本阶段未迁移的 Catalog/System 等调用者保留旧 HTTP 包装，并委托同一实现，避免重复事务逻辑。这里只移动错误边界，不统一整个项目的异常体系。

measurement_slots 与 workbook_export 仅替换异常类型；计划/事实投影、DAG、SQL、Excel、排序和业务状态算法未改动。AF-2 不拆 ORM、不建立 registry、不统一 lifecycle authority、不创建 Analysis 或前端 feature 目录。

自动防回流见[架构依赖测试](../backend/tests/test_architecture_dependencies.py)，DTO 身份、选择性 OpenAPI 与 HTTP 状态/detail/headers 回归见[业务契约测试](../backend/tests/test_growth_contracts.py)。完整 OpenAPI 可在临时内存中比较，无需维护巨型快照文件。

## AF-3：Experiment Core / GER 所有权

Core 拥有 Experiment 稳定身份、类型、名称、owner、通用材料参与关系、生命周期状态和开始/结束/终止原因。GER 拥有默认方案与覆盖值、编号确认/解除、培养皿、巡检、first-N、germinated_at、DAG，以及就绪、完成资格、事实存在和清理判断。原 experiment_config 已移为 germination_config，内部业务算法保留。

`core/experiment_types.py` 的 ExperimentTypeWorkflow 只抽象目前需要的可编辑、PATCH 约束、就绪、完成检查/资格、事实存在及未使用设计清理。Core 不导入 GER 配置、执行、测定实现或 GER ORM；GER 可以依赖 Core 接口及生命周期服务。现有 models/entities.py 保持集中注册，不做表或字段搬迁。

`germination_workflow.germination_registration()` 提供 GER 的 code、原 label 与 workflow；`experiment_composition.build_experiment_registry()` 是唯一静态组装入口，由 create_app 绑定到应用实例。registry 构造时拒绝重复或不匹配的类型元数据，公开接口只提供确定性的 entries 和 require，没有运行时注册/插件扫描。EXPERIMENT_TYPES 保留只读名称兼容视图；GET /api/experiments/types 仍返回原 value/label。没有数据库类型表、第二类型或未来能力占位。

`services/experiment_lifecycle.py` 是唯一正式状态及时间戳写入 authority：update/set_status、reopen_after_cleanup、activate_from_fact、correct_started_at、complete、terminate。GER 负责验证和修改自己的事实，再调用 Core，沿用同一事务及既有审计形状；专用完成/终止与 PATCH 快照仍保持原差异。未使用实验删除时，Core 通过 workflow 检查事实并清理 GER 行，再删除通用材料关系及 Experiment。

首次有效置床只把 ready 转为 active 一次；后续较晚置床不改 started_at。补录更早事实或实际置床时间纠错仍按既有契约维护最早真实置床时间，不冻结成首次录入时间。ORM 默认草稿、测试 fixture、既有 migration 与独立历史 importer/backfill 的历史赋值不属于在线正式 lifecycle 入口，保持原样。

边界及写入保护见[架构测试](../backend/tests/test_architecture_dependencies.py)，静态组装见[registry 测试](../backend/tests/test_experiment_registry.py)，首次置床、审计与跨边界回滚见[lifecycle authority 测试](../backend/tests/test_lifecycle_authority.py)。Measurement/DAG/Excel 算法及前端目录继续留待后续阶段。

## Target Architecture：逻辑目标，尚未迁移

以下是未来职责边界，不代表已创建对应业务模块、ORM、表或新 API。**Logical target != current physical schema。** AF-1 落实运维安全基础，AF-2 调整增长域契约及依赖方向，AF-3 落实 Core / GER 逻辑边界及生命周期 authority；现有正式 v0.5.1 EXE/ZIP 保持原样。

| 逻辑范围 | 目标职责 | 当前实现状态 |
| --- | --- | --- |
| Platform | 配置、认证、会话、公共时间与路径能力 | 已有公共能力，目录和依赖边界待整理 |
| Catalog | Taxon、SeedLot、材料导入与台账 | 当前共享资源库；不因实验类型复制材料身份 |
| Experiment Core | 稳定实验身份、基础描述、材料参与关系、通用生命周期及 registry 接口 | 已通过 workflow 反转 GER 决策依赖；物理 ORM 结构保持 |
| GER | 萌发方案、覆盖值、编号、培养皿、巡检、first-N、DAG 及 GER 决策 | germination_config / germination_workflow / sowing_workflow / germination_execution 明确逻辑归属；未建立新 ORM 模块 |
| Measurement | 时间点、实际样本与测定、计划/事实投影 | 当前仅根苗长；共享中立 contracts，仍依赖 GER 实体 |
| Analysis | 基于设计全集与真实事实的后续分析 | 尚未实现；不提前建立空模型或统计功能 |
| Audit | 所有关键写入事务的前后快照与可读履历 | 当前统一 AuditLog，后续移动服务仍须保留写入 |
| Operations | 生产启动、升级、安全检查与正式数据库备份 | AF-1 源码已实现受控升级及显式数据库恢复；程序版本槽位管理留待 AF-1.x |

## 后续风险与行为边界

- AF-1：已接入统一升级准备入口；旧的受支持数据库须先建立并核验恢复快照，不兼容或验证失败时禁止启动。程序 Current/Previous/Staging 管理和完整保留策略留待 AF-1.x，契约及限制见[生产运维](10_生产部署与控制中心设计.md)。
- AF-2：增长域服务已改用中立 contracts 与轻量业务异常，由 API 映射原 HTTP 响应；Auth/Catalog/System 保留既有适配方式。AF-3 已将 GER 配置及完成判断归入 GER，并收口正式生命周期写入。
- AF-3：PATCH、专用 complete/terminate、首次置床、解除编号确认及开始时间纠错共用 Core 写入 authority；仍保留各入口的校验次序、时间串与审计快照差异。
- AF-4：Python 与 SQLite 独立计算 DAG 计划日期；实际任务投影 measurement_query 与设计全集 measurement_slots 服务不同用途，不能合并后丢失无实际幼苗的材料。
- AF-5：前端实验页面、集中类型和执行子组件包含 GER 假设；execution API 仍有 SQL 和置床清单 Excel 构造，迁移时须保护路由、表头及现场编号。
- 可后延：基础资源列表最多 500 条、客户端分页；Vite 大 chunk、既有测试客户端弃用提示和控制中心关于页写死旧 schema 展示值，单独评估。AF-3 不扩展这些范围，也不通过升级依赖消除提示。

阶段顺序以[开发路线图](03_开发路线图.md)为准；以上风险归类只是后续审计入口，不替代各阶段任务定义。
